# 同步边界说明：同步什么、不同步什么、会出什么问题

> 这份文档回答三个问题，全部结论都来自**实际跑出来的结果**（探针测试 + 真实双设备演练），
> 不是设计意图的推演。写它的目的是：出问题时能一眼查到"这是已知边界"还是"这是 bug"。

---

## 1. 会同步的（6 张表）

用 SQLite 触发器在**任何写入路径**上自动记账，所以不存在"这条路径忘了加同步"的情况。

| 表 | 同步的列 | 说明 |
| --- | --- | --- |
| `groups` | 小组名 | |
| `students` | 姓名、学号、所属小组、是否计入小组总分 | |
| `score_items` | 评分项名称、默认分、说明 | |
| `score_records` | 目标（学生/小组）、分值、原因、评分项、自定义名称、时间、周期、是否快速评分 | 最核心的一张表 |
| `course_schedule` | 星期、课程名、起止时间 | |
| `schedule_adjustment` | 日期、按星期几上课 | 调休 |

**同步的语义**：

- 新增 / 修改 / 删除都会传播；
- 删除是**墓碑**（`deleted_at`），不是物理删除——这样"先删后到"的顺序也不会让数据复活；
- 冲突用 LWW（`rev` 大者胜，相同时比 `rev_device` 字符串序），两端算出的结果一定相同。

## 2. 不会同步的

### 2.1 安全相关（刻意排除）

| 内容 | 为什么排除 |
| --- | --- |
| `pin_hash`（解锁密码哈希） | 同步它等于把大屏的解锁凭据复制到老师电脑上；而且哈希本身不该离开本机 |
| `usb_keys`（USB 密钥） | 硬件绑定，复制到另一台机器没有意义 |

### 2.2 本机外观与偏好

主题色、分析页分栏比例、桌面悬浮课表的位置/透明度/缩放/点击穿透、
天气城市与缓存、托盘行为、锁定时的窗口行为、开机自启 —— 全部是 `app_settings` 里的键，
**不同步**。两台机器屏幕尺寸不同，同步这些只会互相打架。

### 2.3 计分规则与周期 ✅ 已同步

`app_settings` 现在参与同步，但**只同步白名单里的键**（`syncedSettingKeys`）：

| 键 | 作用 |
| --- | --- |
| `current_period` | 当前周期 |
| `student_initial_score` / `group_initial_score` | 初始分 |
| `group_score_mode` | 小组分算法（求和 / 平均） |
| `score_range_mode` / `score_range_min` / `score_range_max` | 分数范围 |
| `merge_same_rank` / `competition_ranking` | 名次规则 |
| `default_quick_scoring` | 默认快速评分 |

白名单写在 **SQL 触发器的 WHEN 子句**里，不是在 Dart 侧过滤——漏掉一处过滤
就会让主题色跟着跑到别人机器上，而这几乎不可能被及时发现。

> 为了让这张表能参与同步，迁移时把它重建成 `id + key` 结构（原本以 `key` 为主键，
> 没有自增 id，而同步元数据靠 id 定位一行）。

### 2.4 本机外观（明确排除，保持原样）

主题色、分析页分栏比例、桌面悬浮课表的位置/透明度/缩放/点击穿透、天气城市与缓存、
托盘行为、锁定时的窗口行为——全部**不同步**。有测试锁定这一点
（`sync_settings_sync_test.dart` 里"本机外观不同步"那条）。

### 2.5 回收站与操作历史

| 表 | 现状 | 后果 |
| --- | --- | --- |
| `score_record_archives`（回收站） | 不同步 | 大屏删的记录进大屏的回收站，老师端看不到 |
| `score_record_logs`（修改历史） | 不同步 | 「这条记录谁改过」两端各记各的 |

### 2.6 整库操作

导入 / 重置 / 恢复备份跑在 `SyncWriteGuard.suppressed` 里，**这批写入不进 outbox**。
语义上成立（"以本地为准"），但意味着：**大屏恢复备份后，老师端不会自动跟着变**，
需要手动点一次「全量对齐」。

## 3. 会遇到什么同步问题

下面每一条都对应一个已确认的现象和当前的处置方式。

### 3.1 两端离线各自加人，学号撞车 ⚠️ 已修

**现象**：大屏加了 01 号张三，老师电脑离线时加了 01 号李四。合并后**其中一个人消失**。

**原因**：学号是唯一索引，但唯一性只在一台设备内部成立。远端那条 INSERT 撞
`UNIQUE(students.student_number)`，异常在拉取循环里被吞掉，只进一个计数。

**现在的处置**：`SyncTableSpec.localUnique` 声明了这个列，冲突时给**晚到的**那个
改成一个空号（`01` → `02`，若被占则继续往后找）。**先到的保留原号**，人的身份不丢。

**代价**：学号可能不连续，且两端会各自算出不同的新号——但最终会收敛到"两个人都在"。

### 3.2 同一天的调休两端设了不同星期 ⚠️ 已修

**原因**：`date` 唯一，两条都要落库必然冲突。

**现在的处置**：`UniqueConflictPolicy.preferLatest` —— 语义上不允许并存，本地版本更新时
远端旧版整条丢弃，不抛异常。

### 3.3 改调休没反应 ⚠️ 已修

**现象**：同一天第二次设置调休，界面无变化。

**原因**：`upsertScheduleAdjustment` 原本是"先 DELETE 再 INSERT"。墓碑化之后旧行还在，
`date` 唯一约束仍占着，第二条 INSERT 直接撞 UNIQUE，异常被 Provider 吞掉。

**现在的处置**：改成"已有这一天的行（含墓碑）就 UPDATE 改活，否则才 INSERT"。

### 3.4 rev 是 Lamport 逻辑时钟，不是时间戳

> **更正**：本文档早期版本说 rev 是"各设备独立的计数器"，**这个说法是错的**。
> 实测：A 连写 10 次得到 rev 1–10，B 应用后 lamport 抬到 10，B 再写得到 **rev 11**。
> 即每次写入都把全局 lamport +1，应用远端事件时还会抬到远端最大值
> （`_applyInner` 里的 `MAX(lamport, event.rev)`）。这是标准的 Lamport 时钟。

**这意味着**：rev 的大小反映**因果顺序**（"改动发生过多少次"），不是挂钟时间。
因此：

- 「后改的赢」在**有因果传播**的情形下成立：B 看到 A 的改动后再改，B 的 rev 必然更大；
- 但**纯并发**（两端离线各改一次、谁也没看到谁）时，rev 的比较退化为按
  `rev_device` 字符串序裁决——此时"谁先按的鼠标"完全不影响结果。

**对课堂场景的影响**：很小。同一时刻基本只有一台在改，且改动会很快传播。

**但不要拿 rev 当"最后修改时间"展示**——它是逻辑计数，不是时间。
要展示时间请用 `updated_at`（本地写入时用 `strftime('now','localtime')` 记录）。

### 3.5 删掉学生会留下孤儿的评分记录 ⚠️ 已修

**现象**：删掉张三，他名下 5 条评分记录仍留在表里，target_id 指向墓碑行。

**原因**：墓碑化之后 `ON DELETE CASCADE` 不会触发（根本没有物理删除）。

**实测到的口径不一致**：删掉一个考了 100 分的学生后，
**班级总正分仍是 103**（把已删学生的分算进去了），
但**小组总分已经变成 3**（因为按 students 表关联，墓碑行 JOIN 不上）。
同一份数据，两个报表给出互相矛盾的数字。

**现在的处置**：`orphanRecordFilter` / `orphanGroupRecordFilter` 加进**所有统计聚合**
（总分、分布、日均），统计口径统一排除孤儿记录；
**「评分变动记录」明细则保留历史**，不因为删了人就消失。

### 3.6 删掉评分项，历史记录显示旧名字

**现象**：删除「课堂表现」这个评分项后，历史记录里仍然显示"课堂表现"。

**原因**：连表用的是 `LEFT JOIN score_items`，墓碑行仍然 JOIN 上了。

**评价**：这**大概率是正确行为**（历史记录不该因为删了预设项就变成"未分类"），
但属于"没明确决策过的默认结果"，需要确认。

### 3.7 刷新课表会产生大量墓碑事件 ⚠️ 已修

**实测（修前）**：5 门课整表替换成 1 门 → **5 条墓碑 + 1 条新增 = 6 条事件**，
且所有课的 uid 全换了，对端看到的是"整个课表被删掉又重建"。

**现在的处置**：`replaceAllCourseSchedules` 改成按
`(weekday, course_name, start_time, end_time)` 求差集——
保留仍在的行（uid 不变），只增删真正变化的部分。实测：

| 场景 | 事件数 |
| --- | --- |
| 内容没变再保存一次 | **0** |
| 只删一门课 | **1**（墓碑） |
| 新增一门课 | **1**（新增） |

### 3.8 占位行的悬挂 ✅ 已暴露

父行始终不到（对端把它删干净了）时会留一个空名字的占位行。**不自动删除**——
自动删可能误删真实数据。

现在会在两个地方兜住：

1. 占位行的学号用 `~pending~<uid>` 而不是空串——空串会让第二个占位行撞上
   学号的唯一索引；
2. 设置页会显示「异常占位行：N 行（对端数据不完整，点「全量对齐」可修复）」。

这样它不会以"一个没有名字的学生"的形式永远潜伏在名单里。

### 3.9 服务端离线

**行为**：状态变 `offline`，outbox 继续涨，**App 全部功能照常**。
退避 5s→10s→…→5min 重试。恢复后一轮补完。

这条是设计红线，已经有测试锁定。

### 3.10 一条事件应用失败：重试，而不是跳过

**旧行为（已修）**：`_pull` 对每条事件单独 try/catch，失败只加一个计数，
然后**照常推进游标**。结果是这条事件再也不会被重放 —— 数据永久丢失，
而界面上"有 N 条事件无法应用"的提示会在下一轮成功同步时被清掉。

**现在的处置**：游标只推进到**最后一条成功应用**的事件；失败的事件留在
游标之前，下一轮自然重试。连续失败 3 次才判定为毒事件，跳过并写入
`sync_dead_letters`，在设置页一直可见，直到用户点「全量对齐」重新铺平。

同类的两条也一并修了：
- 不可解码的 outbox 行（未知表名 / 坏 JSON）不再卡在队首，直接丢弃并计入
  「已丢弃事件」；
- 服务端 push 改成逐条 SAVEPOINT，一条坏事件不会让整批 500
  （那会让客户端无限重试同一批）。应答里带 `rejected` 计数。

### 3.11 `applying` 标记不能跨进程残留

`applying` 是持久化在 `sync_state` 里的。进程若死在应用远端事件中途，
标记会停在 `'1'`，此后**所有**写入的触发器 WHEN 都不成立 —— 编辑照常生效、
界面照常刷新、outbox 一条都不涨，同步从此静默停摆。

现在 `configure()` 启动时无条件复位（进程里一定没有同步在跑，复位是安全的），
并且每条事件的应用都在一个事务里，失败整条回滚。

### 3.12 pin_hash 为什么曾经会跑到服务端

白名单写在**触发器**的 WHEN 子句里，但首次会合走的是 `snapshotLocalRows`
—— 它绕开触发器直接扫表。迁移又给 `app_settings` 的所有历史行补了 uid，
于是老用户升级后第一次配对会把整张设置表推上去（实测泄漏了
`pin_hash` / 主题色 / 天气城市）。

两条路径现在共用 `syncedSettingKeys` 这一份白名单；白名单外的行**故意不补
uid**，`snapshotLocalRows` 会跳过它们，这是第二道保险。
回归测试见 `sync_snapshot_whitelist_test.dart`。

## 4. 优先级建议

按"会不会真的出错"排序：

| 状态 | 问题 | 处置 |
| --- | --- | --- |
| ✅ 已修 | 计分规则 / 当前周期不同步 | `app_settings` 白名单同步 |
| ✅ 已修 | 删除学生留下的孤儿记录 | 统计聚合排除、明细保留 |
| ✅ 已修 | 课表整表替换 uid 全换 | 改为按内容求差集 |
| ✅ 已修 | 占位行悬挂不可见 | 学号占位值 + 设置页计数 |
| ✅ 已修 | 两端离线学号撞车会丢人 | 晚到的改号，先到的保留 |
| ✅ 已修 | 同一天调休两端冲突 | 按 rev 裁决，就地覆盖 |
| ✅ 已修 | 改调休没反应 | upsert 改为 update-or-insert |
| ⏳ 待做 | 老师端写入应走唯一的服务端入口 | 教师端接入时一并设计 |
| ⏳ 待做 | 回收站 / 操作历史不同步 | 可接受，暂不处理 |

## 5. 怎么自查

设置页「同步服务」上有两条路：

| 按钮 | 什么时候用 |
| --- | --- |
| 立即同步 | 平时自动跑，不用点 |
| 全量对齐 | 数据看着不对、换过机器、恢复过备份时点一次 |

状态卡片会显示：连接状态、上次成功时间、待推送事件数、最近错误。
如果「最近错误」里有"有 N 条事件无法应用"，说明有数据没进来，需要看日志。
