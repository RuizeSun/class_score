# 首次会合：启用同步之前的数据怎么上去

## 问题

v11 迁移**刻意不**给历史行记 outbox（否则升级当天会凭空多出几千条待推送
事件）。代价是这些行永远不会自己进事件流。实测确认过：v10 库升级后

```
outbox=0  groups=1  settings=1  lamport=0  uid=grp_da7ede7e2b2c0673
```

行在、uid 在、outbox 是空的；而 `_push` 只读 outbox，`bootstrap` 只拉不推，
于是配对之后服务端上什么都没有——历史数据永远上不去。

## 解法：配对后自动跑一次「会合」

`SyncEngine._runInitialSync` 在首次 `syncNow` 时执行，分四种情形：

| 本地 | 服务端 | 动作 |
| --- | --- | --- |
| 空 | 空 | 什么都不做，标记完成 |
| 有 | 空 | 全部活行推到服务端，标记完成 |
| 空 | 有 | 拉快照铺满本地，标记完成 |
| 有 | 有 | **停下来等用户三选一** |

第四种绝不能自动挑一边——那等于替老师决定丢掉哪一份数据。

## 三选一的语义

- **合并**（推荐）：先上传本地（rev 起点取服务端 `max_rev`，保证同 uid 的行
  能盖过旧版本），再拉快照。两边都不丢。
- **保留本地**：同「合并」的推法，语义上是本地内容为准。
- **保留远端**：先拉快照覆盖同 uid 的行，再把**服务端上没有的本地行打成本地
  墓碑**（用 `applying` 开关抑制记账，不会再推回去污染对端）。

## 几条硬约束

- **rev 起点必须大于服务端 `max_rev`**，否则上传的是「更旧的版本」，
  服务端物化表会拒绝更新，表现为「推送成功但服务端还是老数据」。
- 每行 rev 递增 1，不能整批同号——同号会让 LWW 退化成比 `rev_device` 字符串，
  结果不可预期。
- 上传完把本地 `lamport` 抬到这批 rev 之上，否则本地下一次改自己刚推的行会
  拿到更小的号、改不动。
- 判断「本地有没有数据」用 `countLocalRows()`，**不含 `app_settings`**：新建库
  一定有几行默认设置，算进来的话每次配对都会弹「两端都有数据」。

## 服务端 `/sync/summary`

只回计数与最大 rev（`liveRows` / `event_count` / `max_rev`），不下发内容——
判断「服务端是不是空的」不需要内容，而内容可能有几 MB。

## 顺手修掉的两个既有缺陷

两个都是「代码一直在，但从来没真正生效过」，都是这次写测试才暴露：

1. **迁移前备份从未成功。** 它在 `onUpgrade` 里调 `VACUUM INTO`，而 sqflite 把
   `onUpgrade` 包在事务里，VACUUM 不能在事务内跑。异常被 catch 掉只留一行
   debugPrint，所有测试照样是绿的（没人断言过备份文件存在）。
   现在改为在 `openDatabase` **之前**用只读连接探测版本、确认要升级就做文件级
   复制；备份目录从被打开的库路径推出，不再写进 Flutter SDK 目录。
2. **回收站恢复对墓碑行必然失败。** 删除改成墓碑后原行还在表里（id 不变），
   恢复时按原主键 INSERT 必然撞 `UNIQUE(score_records.id)`。现在先探测行是否
   还在：在就原地「复活」（清空 `deleted_at`），不在才插入。
