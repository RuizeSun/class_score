# 同步的传输安全现状

> 结论先行：**默认配置下的通讯是不安全的。** 默认是明文 HTTP，
> 配对码和设备 token 都以明文经过网络；任何能访问该端口的人拿到 token 就能
> 冒充那台设备读写数据。
>
> 这些结论都是实测出来的（抓包、解库、暴力尝试），不是推测。
> 本轮已经补上 TLS 支持与限流，但**默认仍然需要显式开启**。

---

## 1. 实测发现的四个问题

### 1.1 传输是明文 HTTP

服务端默认 `http://`，没有 TLS。实测抓到一个配对请求的原始字节：

```
HTTP/1.1 200 OK
content-type: application/json; charset=utf-8

{"token":"d71c675fdc83c5f7cc00c53c5a0635d894e8979b4affbbb164ed527c69dad1fb"}
```

token 直接出现在 TCP 负载里。拿到它就能冒充设备：

```
curl -X POST http://127.0.0.1:8801/sync/push \
  -H "authorization: Bearer <抓到或猜到的 token>" \
  -d '{"events":[{...任意伪造的评分...}]}'
→ {"accepted":1}
```

服务端只靠 Bearer token 鉴权，没有和设备指纹、IP 等任何东西绑定。

**影响范围**：同一局域网内（学校网络里的任何一台机器）都能截获。

### 1.2 "哈希"其实是 base64 编码，可逆

`_hash` 的实现是：

```dart
base64Url.encode(utf8.encode('class_score::' + token))
```

注释写的是"服务端只存哈希：库泄露也无法直接拿来登录"，但 base64 是**编码**不是哈希。
实测从库里那一列直接解出了明文 token 并成功登录：

```
库里存的 : Y2xhc3Nfc2NvcmU6OmQ3MWM2...
直接解码 : class_score::d71c675fdc83c5f7c...
能否登录 : True
```

### 1.3 配对码没有限流

配对码是 6 位数字（100 万种）。实测连发 40 次错误码，全部是 401，
没有任何锁定或延迟，服务端也不记录失败尝试（库里没有相关表）。
按 17 次/秒的速度，穷举完整个空间约需 17 小时。

### 1.4 升级时缺列会直接崩溃

给 `pairing` 表加列后，旧库（`CREATE TABLE IF NOT EXISTS` 不会补列）在
**发配对码时**抛 `table pairing has no column named used_at` 并退出。
这个是在真实升级演练里炸出来的，不是静态检查能发现的。

## 2. 本轮修了什么

| 问题 | 处置 | 验证 |
| --- | --- | --- |
| 明文 HTTP | 服务端支持 `--cert/--key` 启用 TLS | TLSv1.3 握手成功；明文打 TLS 端口失败 |
| 无 TLS 警告 | 未启用时启动横幅明确警告 | 见下方 |
| 可逆"哈希" | 改为 `sha256(salt + token)`，前缀 `v2` 区分新旧 | base64 解不出、库里不含明文 |
| 旧库迁移 | 启动时自动把旧格式升级，已配对设备无需重配 | 旧 token 迁移后仍可正常拉取（200） |
| 配对码无限流 | 按来源 IP 计数，10 次失败锁 15 分钟 | 第 11 次起返回 429 |
| 升级崩溃 | `_ensureColumn` 补列 | 旧库启动正常 |

### 客户端侧

- 支持 `trustedCertificatePem`：把服务端那张证书（PEM）**按内容固定**下来。
  这不是"跳过校验"——只接受与指定证书逐字节相同的证书，换一张就拒。
- 设置页新增"服务端证书文件"输入框（仅 https 时有意义）。
- 不给证书时，自签名服务端**被拒绝**（已测）。

### 启用方式

```bash
# 生成自签名证书（局域网用；SAN 写上服务端的实际 IP）
openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout key.pem -out cert.pem -days 365 \
  -config openssl.cnf

# 启动
class_score_server.exe --db data/server.db --port 8787 \
  --cert cert.pem --key key.pem

# App：设置 → 同步服务 → 填 https://<IP>:8787 + 配对码 + 证书文件路径
```

不启用 TLS 时会看到：

```
  !! 未启用 HTTPS：配对码与设备 token 会以明文经过网络，
     同一局域网内任何人都能截获并冒充这台设备。
     生产环境请用 --cert/--key 提供证书，或置于 HTTPS 反向代理之后。
```

## 3. 仍然存在的风险（TLS 也解决不了）

### 3.1 token 等同于设备身份，没有二次因素

拿到 token 就能读写。TLS 只保证"传输路上没被看"，不保证"拿着 token 的人是谁"。
如果老师电脑中木马，token 被读走，攻击者依然可以冒充——这需要设备绑定或
短期 token + 刷新机制，本轮没做。

### 3.2 审计日志只覆盖管理操作 ✅ 部分已补

- **管理后台的所有操作已审计**（登录、生成配对码、撤销设备、编辑数据，
  编辑含 `before`/`after`），见 `docs/sync-admin-console.md` §7；
- **设备同步流量仍然不审计**：每次评分都记一条会把库撑大，而那是自动行为、
  没有人工介入可追。真要追可以按 `events.device_id` + `created_at` 反查，
  事件本身就带来源设备。

### 3.3 证书固定目前是全有或全无

客户端要么信任指定证书，要么完全拒绝自签名。没有做公网 CA 的完整校验路径
测试（用真实域名 + Let's Encrypt 应该能直接工作，但没验证过）。

### 3.4 公网暴露仍需谨慎

本方案假定服务端在**局域网**内。若要放到公网，建议：

- 前面挂 Nginx/Caddy 做 TLS 终止与访问控制；
- 至少加 fail2ban 之类的 IP 封禁，服务端自身的限流只是第一道；
- 考虑只允许校园网出口 IP 访问。

## 4. 安全等级的判断

| 场景 | 现状 |
| --- | --- |
| 同一台机器上跑服务端与 App | 可接受（回环流量不出网卡） |
| 局域网内大屏 ↔ 服务端，**未开 TLS** | **不安全**：同网段可嗅探、可冒充 |
| 局域网内大屏 ↔ 服务端，**开了 TLS + 证书固定** | 传输层安全，够用 |
| 公网 | 不建议直接暴露；需要反向代理 + 额外防护 |

**给部署的建议**：即使只在教室里用，也建议开 TLS。
学校网络往往是同一个网段，任何一台学生机都能跑个抓包工具。
