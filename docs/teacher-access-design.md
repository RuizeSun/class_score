# 教师远程评分（大屏离线时）：能力评估与接入方案

> 相关问题：大屏没开时，老师能不能通过服务端评分？
> 答案：**能，但当前方案里服务端只是"同步中转站"，不是"应用服务器"——差的正是这一层，必须补上。**

---

## 1. 先把缺口说清楚

上一份方案里的服务端，职责是：

- 收下 App 推来的事件，分配 `seq`，按游标下发；
- 做只读副本，供看板/Bot 查询。

它**没有**做：

| 缺口 | 说明 |
| --- | --- |
| 身份与权限 | 现在只有"设备 token"。教师用手机访问，需要账号/角色，而不是"某台电脑的令牌" |
| 业务写入口 | `/sync/push` 接收的是"原始事件"，没有校验（分值是否越界、学生是否存在、周期是否合法） |
| 面向人的读接口 | 只有 `/read/ranking`，教师端需要学生列表、记录列表、统计、周期状态 |
| 乐观并发 | 大屏长期离线时，服务端数据会持续变化，教师端必须能容忍"我看到的不是最新" |
| 可观测 | 老师必须知道"我这条记录还在等大屏上线后合并"，而不是默默存进黑洞 |

**这五件事都不难，但确实是 +3~5 天的服务端工作量**，不能靠"同步通道顺便用一下"糊过去。

---

## 2. 能力评估：能胜任，且大屏离线反而是它最擅长的场景

你的诉求本质上是一个**三状态系统**：

```
        ┌──────────────┐  大屏在线 + 教师在线   → 双向实时收敛（理想态）
        │   大屏（VIP） │  大屏离线 + 教师在线   → 教师读到的是"服务端最终态"
        │  本地 SQLite  │  大屏在线 + 教师离线   → 教师本地队列补交
        └──────┬───────┘  两边都离线           → 各自照常工作，谁上线谁合并
               │
        ┌──────▼───────┐
        │   服务端      │  ← 教师（手机/网页/轻客户端）永远只跟它打交道
        │  事件日志+物化 │
        └──────────────┘
```

关键判断有三条：

1. **评分记录是追加型事件**（`score_records` 只增不改，改走 `score_record_logs`）。这意味着"老师在大屏关机时加的分"和"大屏明天开机后自己加的分"**根本不冲突**，合并就是并集。这是这个 app 的数据模型天然送给你的红利——如果换成"修改某一行的总分"这种模型，离线并发会立刻变成噩梦。
2. **大屏回归时可以整段吸收**。大屏开机后 `pull(since=游标)`，一次性能拿到它离线期间老师做的所有事（一晚上几百条也就几十 KB）。
3. **大屏永远不需要"等"老师**。大屏读自己本地库，老师读服务端；两者通过事件流收敛。不存在"老师在线但大屏关机 → 大屏页面空"的情况，因为大屏根本没开机。

反过来说，有几个**真实约束**必须先接受：

- **网络出口**：教室大屏和老师的手机都得能访问到那台服务端。家里/办公室的机器需要公网可达（Cloudflare Tunnel 或 frp），否则"远程评分"在校园网外就是空谈。这是部署问题，不是代码问题，但必须先解决，否则全部白做。
- **延迟感知**：老师点"加分"到服务端确认通常 100–300 ms（走隧道可能 300–800 ms）。UI 必须**乐观更新**（点下去立刻上屏，失败再回滚并提示），否则会显得卡。
- **权威性**：大屏关机期间，服务端是唯一真相；大屏一上线，它必须"先拉后推"，否则会用自己的旧状态覆盖老师的改动。

## 3. 三种让老师"能评分"的形态

| 形态 | 怎么做 | 工程量 | 优点 | 缺点 |
| --- | --- | --- | --- | --- |
| **A. 现有 App 加"轻量模式"** | 抽一个数据源接缝，远端模式下所有读写走 HTTP | **2–3 天** | UI/统计/交互全部免费复用；已验证的代码最多 | 手机上布局不理想（但能用）；需处理"哪些功能不支持" |
| **B. Flutter Web 构建同一套 UI** | `flutter build web` + 远端数据源 | 3–5 天（A 之上 +2 天） | 老师手机浏览器直接开链接，零安装 | Web 端要处理 CORS、本地存储、无法用 `dart:io` 的地方 |
| **C. 独立轻客户端（Flutter 手机/或新写的网页）** | 新写一套面向教师的极简 UI（选学生 → 选评分项 → 提交） | 5–10 天 | 体验最聚焦（3 次点击完成评分） | 要重新做落点/统计等二次功能 |

**推荐 A，然后按需升级到 B**。这个 app 已经有 78 个 Dart 文件、157 个测试，UI 和统计逻辑是最贵的资产；重写一套轻客户端等于把最贵的部分丢掉重来。

A 的具体接法（已核对代码）：

```
现在：  UI/Provider ──► DatabaseHelper.instance ──► sqflite(本地文件)
改造：  UI/Provider ──► DatabaseHelper.instance ──► DataSource 接口
                                                     ├─ LocalDataSource（sqflite，现状不动）
                                                     └─ RemoteDataSource（HTTP，轻量模式）
```

- `DatabaseHelper.instance` 有 **112 处调用、集中在 11 个文件**（7 个 Provider 占 80%），**调用点一行都不用改**，只在 helper 内部按运行模式分派。
- 桌面专用能力需要隔离：`window_manager`(8 文件)、`desktop_multi_window`(3 文件)、`dart:io`(9 文件)。这些在"轻量模式"或 Web 模式下要跳过——`main.dart` 里已经有一个"是不是浮窗引擎"的前置分支（`main.dart:32-39`），可以在同一处加"是不是轻量模式"的分支，不污染主路径。
- `win32` 在 `lib/` 里 **0 处直接使用**（全在 `windows/runner/`），USB 密钥那部分是通过 `Platform.` 探测盘符（`auth_provider.dart`），Web 模式下会自然退化。

## 4. 服务端要补什么（这是真正的增量）

在原有 7 个端点之外加一小组"应用层"接口：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/auth/login` | 教师账号（用户名+密码 / 或一次性配对码），发短期 token |
| GET | `/api/roster` | 小组+学生（含 `uid`，教师端不需要知道本地 id） |
| GET | `/api/records?period=3&student=stu_x` | 记录列表（分页） |
| GET | `/api/stats?period=3` | 排名与汇总（服务端算，教师端不必自己聚合） |
| POST | `/api/score` | **写入口**：`{student_uid, score, reason, client_op_id, occurred_at}` |
| POST | `/api/score/batch` | 批量加分（整组） |
| DELETE | `/api/record/{uid}` | 撤销（写墓碑） |
| GET | `/api/sync-status` | 有多少事件在等大屏吸收 |

**`POST /api/score` 的内部动作**（这是全部精华）：

1. 校验：学生存在、周期合法、分值在计分规则允许范围内（规则从服务端物化副本读）；
2. 生成事件 `{source: "teacher:zhang", uid: 新生成的记录 uid, ...}` 写入 `events`，拿到 `seq`；
3. 同事务 upsert 物化表 → 教师端刷新立即可见；
4. 大屏下次 `pull` 时拿到这条事件（排除 `origin_device_id`，所以不会回推给教师端自己）。

也就是说：**教师远程评分和 App 之间的同步，用的是同一条事件流，没有第二条数据通路**。这是这套架构最省心的地方——不会出现"远程评分是一套逻辑，本地同步又是另一套"的分裂。

对接口的额外要求：

- `client_op_id`（客户端生成的 UUID）做幂等，老师手抖点两次不会加两次分；
- 服务端返回**当前物化版本号**，教师端据此判断是否需要刷新；
- 所有写操作记录 `source`（`teacher:xxx` / `app:screen-01`），出问题时能追。

## 5. 教师端的交互红线

1. **乐观更新 + 可撤销**：点"加分"立刻出现在列表里并显示"同步中"小标记，2 秒内没确认就变"待同步"，永不弹模态框挡路。
2. **永不因为网络卡住**：离线时队列存在教师端本地（`sqflite` 或浏览器 IndexedDB），上线自动补交——**和大屏用的是同一套 outbox 语义**，shared 包里共用。
3. **大屏在线状态可见**：教师端顶部显示"大屏在线（刚刚同步）" / "大屏离线 3 天（你的评分将在开机后合并）"。老师必须知道自己在改什么。
4. **破坏性操作要区分对待**：加分/扣分随便离线做；**切换周期、删除学生、重置**这类操作必须要求"大屏在线"或至少二次确认，因为它们不是并集语义，会真的打架。

## 6. 工期重估

| 阶段 | 内容 | 工期 |
| --- | --- | --- |
| P0 | 本地就绪（v11 迁移、uid、墓碑、outbox、写路径收敛） | 2–3 天 |
| P1 | 同步内核 + 服务端 MVP（push/pull/seq/配对） | 4–6 天 |
| **P1.5** | **应用层接口（auth/roster/stats/score）+ 物化表** | **+3–5 天** |
| **P2** | **教师端轻量模式（DataSource 接缝 + 远端实现 + 离线队列）** | **+2–3 天** |
| P3 | 部署（隧道/TLS/服务守护）+ 灰度 | 1–2 天 |
| P4 | 可选：Web 构建、独立极简界面、Bot | 按需 |

**总计约 12–19 天**（比"只做同步"多约 5–7 天）。如果急着先解决"老师看不到数据"，可以先做只读（大屏离线时用手机查排名），那是一天级别的事。

---

## 7. 一个必须提前做的判断

> "老师远程评分"和"老师远程查看"是两件不同的事，成本差一个数量级。

- **只读**：服务端已有物化副本，加 3 个 GET 接口 + 一个网页/Flutter Web 页面即可，**1–2 天**，风险极低。
- **可写**：多了权限、幂等、校验、离线队列、冲突提示、乐观更新，**5–7 天**，且必须先把 P0 的 uid/outbox 做完，否则写进去的事件没有稳定的身份可指。

建议路径：**先只读（立刻可用）→ 再同步内核 → 最后开放写**。这样每一周都有能拿给老师用的东西，而不是憋两周后一次性交付。
